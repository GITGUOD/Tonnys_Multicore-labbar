requirements:
Each node must be one actor, if you were to spawn N processes, each running node_loop.
No node's logic runs inside some shared/global loop, each one has basically its own concurrent, isolated
processes with its own state, I guess height, excess, adjacency list etc.

We can only share an edge object between two nodes, no otehr info, so there shouldnt be some sort of
information leak between actors.

In other words: two nodes or ways can only know something about each other if they send messages to each one. Or via a shared edge object.

No wake up polling from a controller.

Ack

Vårt villkor är att sändaren skickar ett förslag till mottagaren: Mottagaren kontrollerar vid mottagandet att h(sändare) = h(mottagare) + 1, och accepterar eller avvisar utifrån det
Varför h(sändare) = h(mottagare) + 1, alltså att höjden bara är 1 steg mindre än sändaren. Varför? Jo vi kan bara skicka till en granne som står exakt ett steg lägre än dig (höjdvillkoret).

Men vad händer om vi inte har noder som är 1 enhet lägre? Vi måste då höja våran höjd med en enhet. 
Exempel är att man står på steg 3, grannarna med kvarvarande kapacitet står på steg 3, 4 och 5 (alla samma eller högre och man kan inte pusha till någon). Minsta bland dem är 3.
Då sätter vi våran nya höjd till 3 + 1 = 4. Nu står du på steg 4, och grannen som stod på steg 3 är nu admissible för oss.
Våran tanke är då att pusha → om alla avvisas → relabela → broadcasta → pusha igen → osv, tills excess = 0 eller inga fler grannar med kapacitet finns. Därefter när vi relabalar berättar vi till alla grannar att vi har relabalat.

The controller acts as the root of an environment. When a node activates another node by sending a message, a parent-child relationship is formed. When a node becomes idle and all its children have finished, it sends an acknowledgment back up to its parent. Once the controller receives acknowledgments from all its direct children, it knows the entire system is idle.

Med andra ord: kontrollern aktiverar källan via en start knapp, källan pushar (aktiverar till A) som sedan pushar till B. När B är klar så skickar den upp till källan som en "ACK" och då terminerar systemet. A och B är children till föräldrarn. Varje nod kan ha sin egna förälder
sänkan slut

			pr("node ~p got push_response from ~p, Admissible = ~p, E = ~p, Pending = ~p~n", [Node, Sender, Admissible, E, Pending]),
			UpdatedNode = case Admissible of
				true -> % om grannen accepterade pushen
					% här måste vi uppdatera flödet i grafen och minska min excess med det jag skickade
					% vi måste veta hur mycket vi skickade, vilket vi kan få från pending listan, dvs den första kanten i listan
					[I|Rest] = Pending, % tar ut första kanten från pending listan
					Edge = edge(G, I), % hämtar kanten från grafen
					V = other(U, Edge), % hämtar grannens index
					Capacity = available_capacity(G, U, I), % hämtar tillgänglig kapacitet på kanten
					Amount = min(E, Capacity), % hur mycket vi kan pusha är min av excess och tillgänglig kapacitet
					pr("node ~p pushing ~p to ~p on edge ~p~n", [Node, Amount, V, Edge]),
					update_flow(G, I, U, Amount), % uppdaterar flödet i grafen med det jag skickade
					NewE = E - Amount, % uppdaterar min excess med det jag skickade
					pr("node ~p updated flow on edge ~p, NewE = ~p~n", [Node, Edge, NewE]),
					Node#node{e = NewE, pending = Rest}; % returnerar en ny version av Node med uppdaterad excess och pending listan utan den kanten vi just skickade på
				false -> % om grannen inte accepterade pushen
					pr("node ~p push_request to ~p was rejected, E = ~p, Pending = ~p~n", [Node, Sender, E, Pending]),
					Node % returnerar samma Node utan ändringar
			end,
			node_loop(UpdatedNode, C, G); % går tillbaka till att vänta på nästa meddelande med uppdaterad Node
